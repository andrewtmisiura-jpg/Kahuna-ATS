# Tidepool

Kahuna Window Cleaning's hiring system: applicant pages, staff review, texts and email, reports. The product spec is [docs/PLAN.md](docs/PLAN.md) and the schema spec is [docs/DATA_MODEL.md](docs/DATA_MODEL.md).

## Local setup

1. Install Node 22 and pnpm 10, plus Postgres 16 server binaries (`initdb`, `pg_ctl` under `/usr/lib/postgresql/16/bin`, or set `PG_BIN`).
2. `pnpm install`
3. `pnpm db:local:init` creates a cluster in `.pgdata` on port 54329 with the `tidepool` and `tidepool_test` databases (later: `pnpm db:local:start` and `pnpm db:local:stop`).
4. `cp .env.example .env`, set `DEV_AUTH_EMAIL` to your email (outside production that signs you in as an Admin without Google) and `ADMIN_EMAIL` to the first Admin's Google email.
5. `pnpm db:migrate` applies the committed SQL migrations in `drizzle/`.
6. `pnpm db:seed` loads the one-time Phase 1 seed (employer, first Admin, roles, pipelines, picklists, legal text v1, templates, snow form v1 published, window form v1 draft, both openings, the two launch entry codes). Re-running is a no-op; it warns about any `DRAFT` placeholder still in `src/db/seed/owner-input.ts`.
7. `pnpm db:changes` applies the one-time content changes listed in `src/db/changes/index.ts` that have not run yet: the owner's five snow questions as the next snow form version, the Phase 2 message templates, and the snow starter rubric, which publishes snow's AI rubric and turns snow scoring to visible. Each change goes through the same services as the screens, is recorded in `applied_change` and never runs twice, so a second run prints "nothing to do". It refuses, and exits non-zero, if the snow form has an unpublished draft open; publish or discard the draft and run it again.
8. `pnpm dev` and open http://localhost:3000/admin (applicant pages are at `/`).
9. `pnpm typecheck`, `pnpm lint`, `pnpm test` (Vitest against `DATABASE_URL_TEST`, reset on every run) and `pnpm build` are what CI runs.
10. `pnpm test:e2e` runs Playwright against the dev server it starts on port 3100: a phone project for every spec, and a desktop project for the kanban board. `E2E_PORT=<port> pnpm test:e2e` picks another port (`playwright.config.ts` reads it), so two checkouts can run at once. The specs write to the dev database, so run `pnpm db:migrate && pnpm db:seed && pnpm db:changes` first.
11. Schema changes: edit `src/db/schema`, run `pnpm db:generate`, review the SQL in `drizzle/`, commit it. Hand-written SQL (triggers, anything drizzle cannot express) goes in a custom migration: `pnpm exec drizzle-kit generate --custom --name <what>`.
12. `pnpm user:add-admin <email>` creates or re-enables an Admin so the owner is never locked out. `pnpm cron` is the 5-minute job Railway runs as a separate service. `pnpm quo:setup` connects Quo (see Production); without `QUO_API_KEY` it prints one line and does nothing, which is the normal local case.
13. `scripts/readonly-role.sql` creates the `tidepool_readonly` database user for the owner's own queries; run it once by hand as the app's database user (see the comment in the file). It can read every table except `integration_secret` (the Quo webhook signing secret).

## Production

One Railway project with three services:

- **web**: this repo, configured by `railway.json` (Railpack build, the pre-deploy step before every deploy, `pnpm start`, the `/health` check). `railway.json` overrides the service settings, and its `preDeployCommand` is `pnpm db:predeploy`, which runs `pnpm db:migrate && pnpm db:seed && pnpm db:changes && pnpm quo:setup`: migrations, the insert-only seed (a no-op on existing rows), any pending one-time content change, then the Quo connection. A failure in any of the first three stops the deploy and the running version stays up. `pnpm quo:setup` always exits 0, so a Quo problem never blocks a deploy; it logs and emails an alert instead. `ADMIN_EMAIL` must be set on web, because `pnpm db:seed` refuses to run without it.
- **cron**: the same repo with its config file set to `railway.cron.json` in the service settings. That builds `Dockerfile.cron` (Node 22 plus `pg_dump` 18, because production Postgres is version 18) and runs `pnpm cron` every 5 minutes: the 24-hour reminder, the one-on-one reminders (one per booked interview, 5pm the day before), sends, inbox alerts, the 7am digest, the 3am backup to R2, the AI scoring jobs (two minutes a pass, one at a time, under the daily scoring limit) and the heartbeat. Its log line counts each step, for example `interview reminders queued=1 canceled=0 skipped=0` and `jobs claimed=3 succeeded=3 retried=0 dead=0 deferred=0`. See `scripts/RESTORE.md` for the backup and the restore test.
- **Postgres**: Railway's Postgres 18, with its scheduled backups on. Both services reference its `DATABASE_URL`.

Every variable is pasted into Railway, never committed; `.env.example` lists them. Set `TZ=UTC` on both services. Phase 2 adds three:

- `ANTHROPIC_API_KEY`: the Anthropic Console key (with a monthly cap) that AI scoring uses, on the cron service, where scoring jobs run, and on web, for the rubric editor's Try it. Never logged or returned. Without it nothing is scored: jobs wait without losing attempts, the alert address (`ALERT_EMAIL`) gets an hourly "AI scoring is paused" email, and Settings > AI scoring says the key is missing.
- `SCORING_PROVIDER`: leave it unset in production, which means `live`; `fake` uses the deterministic stand-in that calls nothing (the default everywhere else, and what the tests use).
- `SCORING_MODEL`: optional, the model live scoring calls; blank means `claude-opus-5-5`. Each score records the model that answered.

First deploy, in order:

1. Set `CRON_HEARTBEAT_OPTIONAL=true` on web. `/health` needs a cron heartbeat under 15 minutes old, which cannot exist before the cron service has run once; remove the variable after that.
2. Set `ADMIN_EMAIL` on web to the owner's Google email (several separated by commas), then deploy web, then cron.
3. The first pre-deploy (`pnpm db:predeploy`) migrates and seeds the empty database, then applies the one-time changes (snow form v2). Check the deploy log for `[db:seed] inserted` and `[db:changes] applied`; later deploys print "nothing to do" for both.
4. Publish each approved legal text: `pnpm legal:publish <kind> <file.md>` with the kinds `sms_consent`, `privacy_policy`, `sms_terms`, `landing_notice`, `ai_disclosure` and `opt_in_page`. It runs as the Admin named by `LEGAL_PUBLISH_AS`, else `ADMIN_EMAIL`.
5. Quo connects itself. With `QUO_API_KEY` set on web (and `PUBLIC_BASE_URL` set to the app's public https address, e.g. `https://tidepool.kahunawindowcleaning.com`), the next deploy's `pnpm quo:setup` step looks up the hiring number +17632922259 in the Quo workspace and stores its id, then creates the one Tidepool webhook (posting to `<PUBLIC_BASE_URL>/api/webhooks/quo`, the four message events, scoped to the hiring number) and stores its signing secret in the database (`integration_secret`), where the webhook route reads it. Nothing is copied by hand and no secret is printed. Every later deploy sees both done and makes no Quo call. If Quo's response does not confirm the webhook covers only the hiring number, the deploy still stores the secret but alerts you to check the webhook's numbers in Quo (Typhoon's texts must not reach Tidepool). The deploy log shows `[quo:setup] hiring number: ...` and `[quo:setup] webhook: ...`; Settings > Texting shows whether each is connected and the last result. Once the number is connected, texts go out whenever Settings > Texting has texting on (the seed turns it on), so run the real-phone test right after that deploy, or turn texting off first.
   - If the hiring number is not in the workspace the key belongs to, nothing is stored and an alert says how many numbers the key can see (last 4 digits only).
   - If Quo already has a webhook posting to Tidepool's address (for example one made by hand), setup creates nothing and never deletes it, because Quo shows a webhook's secret only when it is created. Either paste that webhook's signing secret into Railway as `QUO_WEBHOOK_SECRET` on web, or delete that one webhook in Quo and redeploy so setup recreates it. `QUO_WEBHOOK_SECRET`, when set, always wins over the stored secret.
   - Setup never updates or deletes any webhook, so Typhoon's stays as it is. `pnpm quo:connect` and `pnpm quo:webhook` run the two steps by hand against whatever `DATABASE_URL` points at.
6. Webhooks: Quo posts to `https://tidepool.kahunawindowcleaning.com/api/webhooks/quo` (created by `quo:setup`; the route answers 503 until a signing secret exists); in Resend, add a webhook for bounces and complaints to `https://tidepool.kahunawindowcleaning.com/api/webhooks/resend` and paste its secret as `RESEND_WEBHOOK_SECRET`.
7. `pnpm user:add-admin <email>` creates or re-enables an Admin if the owner is ever locked out.

Phase 2 deploy (Oct 16, 2026): no migration (its tables shipped earlier in 0007 and 0008). Set `ANTHROPIC_API_KEY` on cron and web first, because `pnpm db:changes` turns snow scoring on: the deploy log shows `[db:changes] applied 2026-10-16-phase2-templates` and `[db:changes] applied 2026-10-16-snow-starter-rubric`, and the next cron pass queues a score for every submitted snow application and works through them under the daily limit (snow form v1 applications have no behavioral answers, so they show "not scored" instead). Then paste the one-on-one booking link in Settings > Message templates; invites cannot go out until it is set. The door check-in kiosk is `/check-in/<session id>`, opened from the session page ("Door check-in") on a tablet signed in as an Admin or Hiring Manager.

Checks before merging: `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build` and `E2E_PORT=<free port> pnpm test:e2e`.

## Layout

- `src/app/(public)` applicant pages, phone-first; `src/app/(admin)` staff pages behind sign-in; `src/app/(auth)` the sign-in page.
- `src/server/services` holds all business logic as plain functions that take a `Db` handle; route handlers and server actions only call them. The core pieces: `time.ts` (the one Central-time helper), `applications/transition.ts` (the only writer of `application_event` and of the cached columns on `application`, including the FCRA gate), `messaging/send.ts` (the single send function: queue, claim with `FOR UPDATE SKIP LOCKED`, the send rules, providers), `messaging/inbound.ts` (STOP, START and HELP), `landing.ts` (the landing matching rules), `tokens.ts` (hashed resume links), `entry-codes.ts`, `audit.ts`, `csv.ts` and `notify.ts` (`notifyAdmin`, one email per kind per hour).
- Message providers live in `src/server/services/messaging/providers`: `quo` (texts, `POST /v1/messages`), `resend` (email) and `sink` (records sends, used outside production and in tests). `MESSAGE_PROVIDERS=live` forces the real ones locally.
- `src/server/auth` is Better Auth (Google sign-in, allowlist, database sessions) and `requireRole`, which reloads the user's status and role from `app_user` on every call (`authorize.ts`). Under the development bypass it maps `DEV_AUTH_EMAIL` to its `app_user` row and creates an Admin row on first use.
- `src/db` is Drizzle: `schema/` one file per area of DATA_MODEL.md, `migrate.ts`, `seed/` (`index.ts` is the seed, `run.ts` the `pnpm db:seed` command), `changes/` (one-time content changes: `index.ts` lists them in order, `runner.ts` applies them, `run.ts` is `pnpm db:changes`; add a change as a new file and a new entry, never edit or remove one that shipped); migrations live in `drizzle/` (`0000` generated, `0001` the hand-written triggers and the nulls-not-distinct partial unique, `0007` the generated Phase 2 tables, `0008` their triggers and the read-only user's grants).
- Database rules: every primary key is an app-generated UUIDv7 (`src/lib/uuid.ts`); `application_event`, `consent_event`, `audit_log` and `review_decision` reject UPDATE and DELETE (SQLSTATE `TP001`); published question, form, legal text and rubric versions and their items or criteria reject edits, and a completed `ai_score` rejects every change but `is_current` (SQLSTATE `TP002`); the Phase 3 purge is the one exemption, through `set local tidepool.purge = 'on'`.
- Phase 2 (`docs/PLAN.md`, shipped Oct 16, 2026): the tables are in `src/db/schema` (`sessions.ts`, `scoring.ts`, `interviews.ts`, `jobs.ts`). Services by area:
  - `sessions/`: attendees ("Who came"), phone and name matching, stars and concerns, and the kiosk check-in.
  - `interviews/` and `assessments/`: interviews with the scorecard (`interviews/categories.ts`) and the ladder test; `config/stages.ts` and `config/roles.ts` are the stage editor and New role.
  - `messaging/`: `template-text.ts` (the template rules, client-safe), `templates.ts` (Settings > Message templates and the booking link), `staff-sends.ts` (Send a message, the invite and decline that travel with a move or close, the status page's booking link) and `interview-reminders.ts`.
  - `scoring/`: the contract (`types.ts`), the 1 to 100 formula and input (`engine.ts`), the snapshot with redaction (`snapshot.ts`), the live scorer (`anthropic.ts`, behind `provider.ts`) and the deterministic fake (`fake.ts`, used everywhere but production), `score-application.ts`, the queueing and daily cap (`jobs.ts`, `rescore.ts`), the rubric editor (`rubrics.ts`), Try it (`test-cases.ts`) and the AI disclosure (`disclosure.ts`).
  - `jobs/`: the job table's queue (`queue.ts`) and the cron's jobs step (`run.ts`).
  Work that belongs inside a transition (the screening review decision, the invite or decline a move or close sends, an interview record) goes in `scoring/`, `messaging/` or `interviews/after-transition.ts`, which `applications/after-transition.ts` calls inside every transition. The profile's Phase 2 panels are in `src/components/admin/applicants/panels`; Settings has Roles and stages, Message templates and AI scoring; a session's floor view is `/admin/sessions/<id>/floor`; the door check-in kiosk is the `(kiosk)` route group at `/check-in/<session id>`; `tests/phase2-flows.test.ts` drives the areas through each other.
- `src/cron/index.ts` is the cron entry point. `railway.json` configures the web service (build, the `pnpm db:predeploy` pre-deploy step, `/health` check); point the cron service at `railway.cron.json` in its Railway settings so it runs `pnpm cron` every 5 minutes without a healthcheck.

Next.js ships its own current documentation in `node_modules/next/dist/docs`; read it before writing App Router code, since conventions moved in version 16 (for example `proxy.ts` replaces `middleware.ts`).

Set `TZ=UTC` wherever the app runs; every timestamp is stored in UTC and reported in Central time through one helper.
